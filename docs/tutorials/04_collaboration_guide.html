一、协作的"地基"：Git 版本管理

打个比方：Git 就像给整个项目装了一个"时光机 + 共享笔记本"。每次有人改动，都像在笔记本上"保存一个版本"，谁改的、什么时候、改了啥，全都有记录。出问题了，随时可以退回上一个版本。

三个关键概念（大白话）：

概念大白话为什么重要
仓库（repo）整个项目的"主笔记本"所有人都在这一个笔记本上协作
提交（commit）保存一个版本，并写一句"我改了啥"让历史可查、可回退
分支（branch）在笔记本上"撕一页纸"自己单独写大家各写各的，写完再合回去，不互相踩

本平台项目的约定：

  • 主分支叫 main（正式版）；
  • 每个人在自己私人的分支上干活（比如 fix-taiwei-adapter）；
  • 干完、测完、验收过，才合并回 main；
  • 只在本机提交，不推送到公共服务器、不部署——改动要负责人（读者）看过才算数。

二、一个人改功能：完整流程（8 步）

1 领任务→ 2 建分支→ 3 改代码→ 4 写测试→ 5 跑全量测试→ 6 提交→ 7 报告证据→ 8 等验收

每一步大白话解释：

步骤做什么为什么
1 领任务明确要改什么、改哪几个文件防止东改西改、范围失控
2 建分支git checkout -b fix-xxx 开一条私人线不影响别人正在写的东西
3 改代码只改任务要求的文件不顺手重构别的模块
4 写测试给新功能加自动测试证明它真能用、以后坏了能发现
5 跑全量测试跑 pytest，全绿才能继续确保没弄坏别人做的东西
6 提交保存版本 + 写清改动说明历史可查
7 报告证据把测试结果、日志、产物路径贴出来用事实说话，不吹牛
8 等验收负责人（读者）看过没问题才合并把关质量
踩过的坑（真实例子）：有一次改"跑 3D 流程"，光说"跑通了"没给证据，结果发现其实连工具都起不来。所以现在规矩是：说成功 = 拿日志和文件来。

三、代码放在哪？—— 每个模块归谁管

项目分了几个"车间"，每个车间管一类事。新同学看一眼就知道改东西该去哪：

目录管什么举例（谁改动找这里）
apps/api后台接口（接收网页请求）加一个新按钮、新功能接口
apps/web网页界面改页面、加表单、改文案
packages/contracts数据格式（合同）改任务单/插件的格式
packages/scheduler排队、调度、进度任务队列、worker 相关
packages/execution跑 EDA 工具2D/3D 流程、适配器
packages/analysis分析、知识、AI 建议自演化、入库、优化
packages/visualization画图版图/原理图显示
integrations插件说明加新 EDA 工具插件
tests自动测试所有改动都要保证这里全绿
铁律：改哪块代码就动哪块，不许顺手改别的车间；动共享的东西（工具链、数据库）必须先打招呼。

四、怎么加一个新插件？（开放平台的核心）

这是本平台平台最值得讲的"开放"之处：想接入一个新的 EDA 工具（比如别的 3D 工具、新的分析器），不用动平台主体，只要按"三件套"插上去：

要交的东西大白话模板/例子
① 插件说明文件
(plugin.json)		 给插件办"身份证"：叫什么、能干什么、需要什么工具 integrations/taiwei_pin_3d/taiwei.plugin.json
② 适配器程序
(adapter.py)		 翻译官：把平台的任务单翻译成工具的指令，跑完再收集产物 packages/execution/.../taiwei_adapter.py
③ 任务单生成器
(plugin.py)		 告诉平台：这个插件接受哪些参数、产出哪些文件 packages/execution/.../taiwei_plugin.py

接入后，平台自动就能：网页提交任务 → 排队 → 调适配器 → 收集产物 → 存档案 → 可追溯。TaiWei 3D 就是这么接进来的，RTLScout、EDACraft 也是。

插件的"插头规格"（技术细节给同学看）：每个插件必须声明自己的 capability（能力标签，如 3D 设计）、artifact_rules（必须产出哪些文件）、adapter_entry（怎么启动）。符合规格就能注册进平台，不用改平台核心代码。

五、测试和验收：怎么保证不弄坏别人

自动测试（pytest）

项目有一套自动测试（现在 214 个用例通过），每次改完代码都要跑一遍：

cd ~/openroad-platform
export PYTHONPATH="packages/contracts/src:packages/execution/src:packages/scheduler/src:packages/analysis/src:packages/visualization/src"
python3 -m pytest -q --no-header
  • 全绿（或只有既知的 2 个环境性失败）→ 可以提交；
  • 变红了 → 说明弄坏了东西，先修好再说。

验收（负责人把关）

每次改动要交三样东西，缺一不可：

  • ① 改了什么（文件清单 + 一句话说明）；
  • ② 测试结果（跑了几条、过没过）；
  • ③ 运行证据（真实跑过：日志/文件/数据库记录）。
诚实铁律：说"成功"必须能拿出证据；拿不出就说"还没验证"。谁也不许用"看起来差不多成功了"这种话蒙混——这是整个团队的信用底线。

六、团队规矩：哪些能做哪些不能做

✅ 可以做❌ 不能做
· 在自己分支上自由改动
· 给功能写测试
· 跑真实任务验证
· 标注 [事实]/[假设] 地讨论问题
· 改自己负责的模块 		· 推送到公共服务器 / 部署
· 删 var/ 里的原始证据
· 改共享工具链（ORFS/OpenROAD/PDK）
· 动用户文档（plan/）
· 没验收就宣称"完成"
· 顺手重构不属于任务的代码
一句话规矩：随便改、随便试，但交出去的东西必须真实、有证据、不越界。

七、新人入门清单

新同学（比如师弟师妹）来了，照着这个清单走：

  1. 读 README——项目是什么、怎么启动（大约半小时）；
  2. 启动平台——按 README 把网页和 worker 跑起来，导入一个设计跑一遍 2D（半天）；
  3. 跑一遍全量测试——确认环境没问题（1 小时）；
  4. 读目录结构——知道改东西去哪找（对照本页第三节）；
  5. 领一个小任务——从修 bug / 补文档 / 加测试开始，走完 8 步流程；
  6. 交第一份作业——改了什么 + 测试结果 + 运行证据，给负责人验收。
给读者的建议：想让大家都能贡献，把这三份讲解（TaiWei 3D / 自演化 / 协作）连同主讲解一起放进 README 的"新手指引"，新人照着就能上手。
