一、先建立心智模型：三个角色一台戏

ORFS 的整个仓库其实只有三样东西在配合，记住这个模型，后面全是对号入座：

角色是什么干什么
总指挥flow/Makefile读"原料单"（config.mk）、按顺序叫工人（每阶段跑一个 openroad 进程）、把中间文件（DEF）传给下一个阶段
工人flow/scripts/*.tcl每个阶段一个 Tcl 脚本，被 openroad 执行，真正调用布局布线算法
原料单designs/…/config.mk + platforms/…/config.mk告诉 Makefile：用哪个设计、哪个工艺、什么参数
一条命令的旅程：make DESIGN_CONFIG=./designs/nangate45/gcd/config.mk → Makefile 读 config.mk（知道设计=gcd、工艺=nangate45、时钟=10ns…）→ 依次执行 synth → floorplan → place → cts → route → finish，每阶段启动一次 openroad -exit 脚本.tcl，前一阶段的产物（DEF）喂给后一阶段。

二、flow/Makefile —— 总指挥

打开 flow/Makefile，前 60 行全是变量定义，这是读懂它的钥匙：

# 你（用户）通过命令行传进来的核心变量
DESIGN_CONFIG ?= ./designs/nangate45/gcd/config.mk   # 指定"设计 + 工艺 + 参数"的原料单
PLATFORM     ?= nangate45     # 工艺（可被 config.mk 覆盖）
DESIGN_NICKNAME ?= gcd        # 设计名（结果目录用）
FLOW_VARIANT ?= base          # 变体名（默认 base；实验可以用 run1/run2 区分）

# 由上面推导出来的路径（make 自动拼）
OBJECTS_DIR  = $(RESULTS_DIR)/$(PLATFORM)/$(DESIGN_NICKNAME)/$(FLOW_VARIANT)
RESULTS_DIR  = results
REPORTS_DIR  = reports
LOGS_DIR     = logs
SYNTH_HOME   = $(abspath .)

然后是一堆目标（target）：

目标干什么
make synth / floorplan / place / cts / route / finish只跑到某一阶段（方便调试/分步看）
make all（默认）从头跑到 finish 出 GDS
make gui打开 OpenROAD GUI 看版图
make clean / clean_all清掉结果/日志
make report汇总生成报告

每个阶段目标的核心动作就一行（以 synth 为例）：

$(OBJECTS_DIR)/1_synth.v: $(DESIGN_CONFIG) $(PLATFORM_DIR)/config.mk $(SCRIPTS_DIR)/synth.tcl
	@mkdir -p $(dir $@)
	openroad -exit scripts/synth.tcl \
		$(abspath $(DESIGN_CONFIG)) $(abspath $(PLATFORM_DIR)/config.mk) \
		> logs/$(PLATFORM)/$(DESIGN_NICKNAME)/$(FLOW_VARIANT)/1_synth.log 2>&1
	@echo "[INFO][FLOW] SYNTHESIS COMPLETED"
读懂这一段的收获：① 每个阶段 = 一个独立的 openroad 进程跑一个 Tcl；② 产物有编号（1_synth、2_floorplan…6_final）；③ 日志写到 logs/ 对应目录；④ Tcl 收到两个参数：设计 config.mk 和工艺 config.mk（都是"原料单"）。

三、config.mk —— 原料单（设计级 + 工艺级）

设计级：designs/<工艺>/<设计>/config.mk

以 gcd 为例（flow/designs/nangate45/gcd/config.mk）：

export DESIGN_NAME  = gcd              # 顶层模块名
export PLATFORM     = nangate45        # 用哪个工艺
export VERILOG_FILES = $(sort $(wildcard $(DESIGN_HOME)/src/gcd/*.v))   # RTL 文件（通配自动收集）
export SDC_FILE     = $(DESIGN_HOME)/nangate45/gcd/constraint.sdc       # 时序约束
export CORE_UTILIZATION = 30           # 核心利用率（这就是你网页上那个数）
export TNS_END_PERCENT = 100

这些 export 的变量会被 Makefile 读进环境，最终传进 Tcl 脚本（getenv 读取）。

工艺级：platforms/<工艺>/config.mk

export PDK_VARIANT = CORE65LPSV1ST
export STD_CELL_LIBRARY = NangateOpenCellLibrary
export LIB_FILES = $(PLATFORM_DIR)/lib/NangateOpenCellLibrary_typical.lib
export LEF_FILES = $(PLATFORM_DIR)/lef/NangateOpenCellLibrary.lef
export TECH_LEF  = $(PLATFORM_DIR)/lef/NangateOpenCellLibrary.tech.lef
export MIN_ROUTING_LAYER = M2
export MAX_ROUTING_LAYER = M10
export MIN_PIN_WIDTH = 0.2
一句话：设计 config.mk 说"这个设计长什么样"，工艺 config.mk 说"这家工厂有什么材料"。Makefile 把两份都读进来，Tcl 按变量干活。

四、flow/scripts —— 工人（每阶段 Tcl 怎么被调用）

flow/scripts/ 下每个阶段一个 Tcl，另有 common/ 放公共逻辑：

flow/scripts/ ├── common/ ← 公共部分（平台初始化、电源连接、单元改尺寸等） ├── synth.tcl ← 综合（读 RTL → Yosys/ABC → 网表） ├── floorplan.tcl ← 布局规划（die/IO/电源网格） ├── global_place.tcl + detail_place.tcl ← 布局（分两步：全局 + 详细） ├── cts.tcl ← 时钟树（TritonCTS） ├── global_route.tcl + detail_route.tcl ← 布线（分两步：全局 + 详细） ├── density_fill.tcl ← 金属填充 ├── finish.tcl ← 终检（DRC/GDS 导出）及相关脚本（cdl/检查） └── utils.tcl ← 工具函数（写报告、算指标）

每个阶段 Tcl 的骨架（以 synth.tcl 为例）几乎都是"读入 → 干活 → 报告 → 写中间文件"：

source scripts/common/platform.tcl          # 1. 公共初始化：加载工艺/设计变量
read_verilog $env(DESIGN_HOME)/src/gcd/gcd.v  # 2. 读设计
…
synth -top gcd -liberty $env(LIB_FILES)     # 3. 调用综合
write_verilog $OBJECTS_DIR/1_synth.v        # 4. 写中间产物（下一个阶段的输入）
report_checks > $REPORTS_DIR/…/1_synth.check  # 5. 写报告
关键认知：阶段之间的"接力棒"是文件——1_synth.v（网表）喂给 floorplan，2_floorplan.def（版图）喂给 place，以此类推。想改流程？要么改 Makefile 的调用，要么改对应 Tcl。这就是"代码组织"的核心：每个阶段独立、靠文件接力、用变量沟通。

五、结果去哪了：results / reports / logs

跑完一次，flow/ 下会出现三个目录，结构完全镜像：

flow/ ├── results/<工艺>/<设计>/<变体>/ ← 真正的产物 │ ├── 1_synth.v ← 网表 │ ├── 2_floorplan.def ← 布局规划版图 │ ├── 3_place.def ← 布局版图 │ ├── 4_cts.def ← 时钟树版图 │ ├── 5_route.def ← 布线版图 │ ├── 6_final.def / 6_final.gds / 6_final.odb ← 最终版图（GDS = 拿去制造） │ └── 6_final.v ← 最终网表（含时钟缓冲） ├── reports/<工艺>/<设计>/<变体>/ ← 每个阶段的报告 │ ├── 1_synth.stat.rpt / 1_synth.check │ ├── 5_route.drc ← 布线 DRC 报告 │ └── 6_final.metrics ← 最终指标（面积/时序/DRC） └── logs/<工艺>/<设计>/<变体>/ ← 每阶段完整日志（报错先看这里）

平台读的就是 6_final.metrics 和 6_final.gds 这类文件，转成 openroad_eval.json 的指标。

六、platforms —— 工艺库是怎么组织的

flow/platforms/ ├── nangate45/ ← 一个工艺一个目录（教学常用，免费） │ ├── config.mk ← 工艺"原料单"（上面讲过） │ ├── lib/ ← 单元时序库（.lib：每个门多快/多费电） │ ├── lef/ ← 单元几何（.lef：每个门多大/引脚在哪） │ ├── cells/ ← 单元版图（.gds 等，可选） │ ├── tracks/ ← 布线轨道定义 │ └── sky130hd/ ← 开源工艺（SkyWater 130nm，真实可流片） │ └── asap7/ ← 先进节点（7nm 预测模型，学术用） │ └── gf180mcu/ ← GlobalFoundries 180nm

一个工艺 = config.mk（怎么用）+ lib（时序）+ lef（几何），三者缺一不可。这也是为什么"换工艺"是件大事：全套材料都要换，还要重新综合映射。

七、tools 和构建脚本

OpenROAD-flow-scripts/ ├── tools/ ← 工具源码（submodule） │ ├── OpenROAD/ ← OpenROAD 本体（C++，物理设计引擎） │ ├── OpenROAD-flow-scripts/…/yosys/ ← Yosys 源码（综合前端） │ └── install/ ← 编译产物（openroad、yosys 二进制） ├── build_openroad.sh ← 一键编译（拉 submodule → cmake → 装到 tools/install） └── env.sh ← 设置环境变量（PATH、LD_LIBRARY_PATH），每次用前 source
记忆锚点：源码在 tools/，编译产物在 tools/install/bin，env.sh 把二进制加进 PATH——跑 ORFS 前先 source env.sh。我们平台的 2D 工具链就是装好的这一整套（~/OpenROAD-flow-scripts）。

八、实操：追代码路线图（vibe coder 专用）

以后遇到"看不懂"或"想改点东西"，按这个路线追，比瞎猜快十倍：

  1. 先看原料单：designs/nangate45/gcd/config.mk —— 这个设计/工艺用什么参数（1 分钟）；
  2. 再找 Makefile 对应目标：grep -n "1_synth" flow/Makefile —— 看这一阶段调用了哪个 Tcl、传了什么（2 分钟）；
  3. 打开那个 Tcl：flow/scripts/synth.tcl —— 从上往下读"读入→干活→报告"（5 分钟）；
  4. 卡住了看日志：logs/nangate45/gcd/base/1_synth.log —— 报错/警告都在里面；
  5. 想改参数：优先改 config.mk 的 export CORE_UTILIZATION=…（不用动代码）；想改流程逻辑才动 Tcl。
vibe coder 的三个常见误区：① 以为要读懂所有代码——其实 80% 的活靠 config.mk 变量和几个 Tcl 入口；② 在错误的地方找日志——日志永远在 logs/，不是控制台；③ 不敢改——先复制 config.mk 改成 FLOW_VARIANT=myexp，跑坏了大不了 make clean，零风险试错。
进阶练习（30 分钟上手）：① 打开 gcd 的 config.mk 把利用率改成 50 重跑，对比 6_final.metrics；② 打开 global_place.tcl 和 detail_place.tcl，知道布局就"全局布局 + 详细布局"两步；③ 打开 finish.tcl 找到 write_gds 看 GDS 怎么导出的——三个练习做完，你就不再是黑盒使用者了。

九、常见疑问

Q1：我改 config.mk 需要重新编译吗？

不需要。config.mk 是运行时配置，改完直接 make 重跑即可（Makefile 会因文件变化自动重跑受影响阶段）。

Q2：想加一个新设计怎么做？

三步：① 在 designs/src/<name>/ 放 RTL；② 在 designs/<工艺>/<name>/config.mk 写配置（参考 gcd 的抄）；③ make DESIGN_CONFIG=…。平台里"导入设计"就是帮你做了前两步。

Q3：3D 流程（ORFS-Research）和这个结构一样吗？

基本一样（Makefile + Tcl + config.mk），只是多了 3D 平台（asap7_3D）和 3D 专用脚本（分层、跨层布线）。所以看懂 2D 的结构，3D 也八九不离十。

Q4：这些 Tcl 是 OpenROAD 特有的语言吗？

Tcl 是通用脚本语言（OpenROAD 用它做交互式命令入口）。命令如 read_verilog、global_placement 是 OpenROAD 注册的命令——用 openroad -help 或 GUI 里 help 命令名 可查。
